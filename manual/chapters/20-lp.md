# 20. The LP and MIP interface {#ch-20}

This chapter describes the interface through which a program builds a Linear
Program (LP) or a Mixed Integer Program (MIP) and has it solved by an external
solver. The interface is declared in `lp_base.h`, the default solvers are
chosen in `lp.h`, the skeletons of `lp_skeleton.h` do nothing but compile, and
`glpk.h`, `cplex.h`, `clp.h`, `cbc.h` and `soplex.h` connect the interface to
GLPK, CPLEX, Clp, Cbc and SoPlex. Unlike the rest of the library, these
classes are not templates: they are compiled into the library, each backend
only when its solver is found at configuration time ([chapter
2](02-installation.md#ch-2)). A program written against the base classes
compiles with any backend; it also compiles with none, although then only the
skeletons are available.

## 20.1 The structure of the interface {#sec-20-1}

We are concerned with problems of the form

$$
\min\ (\text{or}\ \max)\ \ c^\top x + c_0 \quad\text{s.t.}\quad l^r \le A x \le u^r ,\quad l^c \le x \le u^c ,\quad x_j \in \mathbb{Z}\ \ (j\in J) , \tag{20.1}
$$

where each row $i$ of $A$ has the bounds $l^r_i\in\mathbb{R}\cup\{-\infty\}$
and $u^r_i\in\mathbb{R}\cup\{+\infty\}$, each column $j$ has the bounds
$l^c_j$ and $u^c_j$ alike, $c_0$ is a constant, and $J$ is the set of the
integer columns, which is empty for an LP. A row with $l^r_i=u^r_i$ is an
equation, and one with both bounds finite is a *range* constraint. The
interface describes (20.1) with three classes (Figure 20.1): `LpBase` holds
the model, i.e., the columns, the rows, the coefficients, the bounds and the
objective; `LpSolver` adds the solution of an LP, with its dual values and its
basis; `MipSolver` adds the integrality of the columns and the solution of a
MIP. Both `LpSolver` and `MipSolver` derive virtually from `LpBase`, and a
backend derives from one of them. Hence, a function that takes an `LpSolver &`
works with any LP backend, and one that takes an `LpBase &` builds a model for
both kinds of solvers.

![Figure 20.1. The classes of the interface: the model is held by `LpBase` (primary), the solving and the solution by `LpSolver` and `MipSolver` (primary), and each backend (the added colour) derives from one of the two. The common bases `GlpkBase`, `CplexBase` and `SkeletonSolverBase` are not drawn.](../figures/20-classes.svg){#fig-20-1}

All the numbers of the interface are of the type `LpBase::Value`, which is
`double`. The constants `LpBase::INF` and `LpBase::NaN` are the infinity and
the quiet NaN of `double`; an infinite bound is written as `INF` or `-INF`,
and NaN marks an unset bound of a constraint ([§20.2](20-lp.md#sec-20-2)). The
enumerations of `LpBase` are `Sense` (`MIN`, `MAX`), `MessageLevel`
(`MESSAGE_NOTHING`, `MESSAGE_ERROR`, `MESSAGE_WARNING`, `MESSAGE_NORMAL`,
`MESSAGE_VERBOSE`) and `SolveExitStatus`. The last one is the value returned
by `solve()`: it is `SOLVED` (0) when the solver has found an optimal solution
or proved the problem infeasible or unbounded, and `UNSOLVED` (1) in any other
case, e.g., when a limit of the solver stopped it. Whether a solved problem is
optimal, infeasible or unbounded is then read from the *problem type*
([§20.4](20-lp.md#sec-20-4) and [§20.5](20-lp.md#sec-20-5)).

Then `lp.h` defines the default solvers. When at least one backend is found at
configuration time, the macro `LEMON_HAVE_LP` (and, for GLPK, CPLEX and Cbc,
`LEMON_HAVE_MIP`) is defined in `lemon/config.h`, together with
`LEMON_HAVE_GLPK`, `LEMON_HAVE_CPLEX`, `LEMON_HAVE_CLP`, `LEMON_HAVE_CBC` and
`LEMON_HAVE_SOPLEX` for the backends found. In this case `Lp` is the default
LP solver, and `Mip` the default MIP solver. Usually the CMake options
`LEMON_DEFAULT_LP` and `LEMON_DEFAULT_MIP` choose them; when they are not
given, or they name a solver that was not found, the first solver found is
taken in the order CPLEX, Clp (with Cbc for the MIP), GLPK, SoPlex. SoPlex is
an LP solver only, and therefore `Mip` is not defined when it is the only
backend; neither `Lp` nor `Mip` is defined when no backend is found. A program
that must compile in all cases guards their use with `#ifdef LEMON_HAVE_LP`
and `#ifdef LEMON_HAVE_MIP`, as `test/lp_test.cc` and `test/mip_test.cc` do,
and as the example of [§20.8](20-lp.md#sec-20-8) does.

## 20.2 Columns, rows and expressions {#sec-20-2}

A column (a variable) is referred to by an object of the class `LpBase::Col`,
and a row (a constraint) by an object of `LpBase::Row`. These handles behave
as the items of a graph ([chapter 3](03-mental-model.md#ch-3)): they are
copied freely, they compare with `==`, `!=` and `<` (an artificial order, for
the associative containers), a default constructed one is undefined, and one
constructed from `INVALID` is invalid. A handle stays valid when other columns
or rows are added or erased, since the interface keeps its own index of the
columns and of the rows and translates it into the indices of the solver. The
static functions `id(col)`, `colFromId(id)`, `id(row)` and `rowFromId(id)`
convert between a handle and its integer id. The iterators `ColIt` and
`RowIt`, constructed from the solver, list the columns and the rows, and
`cols()` and `rows()` return ranges for the loops of C++11.

A linear expression of the columns with a constant term is an object of the
class `LpBase::Expr`. It stores the nonzero coefficients in a `std::map` from
the column id to the value, and the constant apart. A number and a column
convert implicitly to an `Expr`, and the operators `+`, `-`, `*` and `/` by a
number, with their compound forms, combine expressions; for instance,
`2 * x + 3 * (y - x) + 4` is the expression $-x+3y+4$. The coefficient of a
column is read with `e[c]` (zero when absent) and changed through the
reference returned by the non-constant `e[c]`, and the constant term is
accessed by the unary `*e`. Also, `clear()` sets everything to zero,
`simplify(eps)` removes the coefficients whose absolute value is at most `eps`
(by default 0) and sets the constant to zero under the same condition, and the
iterators `CoeffIt` and `ConstCoeffIt` list the terms, converting to the
column of the term and dereferencing to its coefficient. Note that `set(c, v)`
removes the term when `v` is zero, but otherwise inserts it only when the
column has no term yet, since it calls `std::map::insert`; one changes an
existing coefficient through `e[c] = v`.

A constraint is an object of the class `LpBase::Constr`, made of an expression
and of a lower and an upper bound, read and written by `expr()`,
`lowerBound()` and `upperBound()`; `lowerBounded()` and `upperBounded()` tell
whether a bound is set and finite. A bound equal to NaN is unset, which is the
state of both bounds of a default constructed constraint. The comparison
operators between expressions and numbers build constraints, as Table 20.1
shows.

| Written | Lower bound | Expression | Upper bound |
|---|---|---|---|
| `e <= s` | unset | `e` | `s` |
| `s <= e` | `s` | `e` | unset |
| `e <= f` | 0 | `f - e` | unset |
| `e == s` | `s` | `e` | `s` |
| `e == f` | 0 | `f - e` | 0 |
| `(s <= e) <= t` | `s` | `e` | `t` |

<span id="tab-20-1"></span>**Table 20.1.** The constraints built by the
comparison operators, `e` and `f` expressions (or columns) and `s` and `t`
numbers; `>=` gives the mirrored cases.

A second bound can be added to a constraint by comparing it with a number, as
in the last row of Table 20.1, but only on the side that is still unset. This
is checked at run time by `LEMON_ASSERT`, and hence a wrong double comparison
such as `x[1] <= x[2] <= 5` compiles but fails the assertion (when assertions
are enabled, [chapter 8](08-auxiliary.md#ch-8)). Since C++ evaluates
`s <= e <= t` as `(s <= e) <= t`, the form `-3 <= v <= 4` builds the range
constraint intended. When a constraint is added to the model, its constant
term is moved to the bounds, i.e., the row $l \le a^\top x + c \le u$ is
stored as $l-c \le a^\top x \le u-c$, and an unset or infinite bound becomes
$\mp\infty$.

Similarly, `LpBase::DualExpr` is the analogous expression of the rows, i.e., a
column of the matrix, or a linear combination of the dual variables; it has
the same members as `Expr` except the constant term. Rows convert to it
implicitly, and it is used to set or read a whole column
([§20.3](20-lp.md#sec-20-3)) and to evaluate a combination of the dual values
([§20.4](20-lp.md#sec-20-4)).

## 20.3 Building and modifying a problem {#sec-20-3}

We now list the members of `LpBase` that build and change the model; all of
them work through the virtual functions of the backend, and therefore their
cost is the one of the solver. A column is added by `addCol()`, which gives an
empty column with the bounds $-\infty$ and $+\infty$ in all the backends of
the library, and by `addCol(e, o)`, which also sets its coefficients from the
`DualExpr` `e` and its objective coefficient to `o` (0 by default). The
function `addColSet(t)` fills a container with new columns and returns their
number; `t` can be a container of `Col` (e.g., a `std::vector`), an
associative container whose mapped type is `Col` (e.g., a
`std::map< K , Col >`), or a writable map of the library with values of type
`Col`, e.g., a `ListDigraph::ArcMap< LpBase::Col >`, which gives one column
per arc. The rows are added in the same ways: `addRow()` gives an empty row,
`addRowSet(t)` fills a container, and `addRow(l, e, u)` and `addRow(c)` add a
row from an expression with two bounds or from a constraint, moving the
constant term as described in [§20.2](20-lp.md#sec-20-2).

Once created, a column is changed by `col(c, e)`, which sets its coefficients,
and read back as a `DualExpr` by `col(c)`; the analogous `row(r, l, e, u)` and
`row(r, c)` set a row, and `row(r)` returns its coefficients as an `Expr`. A
single coefficient is set and read by `coeff(r, c, v)` and `coeff(r, c)`, and
`erase(c)` and `erase(r)` remove a column or a row. The bounds are set and
read by `colLowerBound(c, v)`, `colUpperBound(c, v)`, `colBounds(c, l, u)`,
`rowLowerBound(r, v)` and `rowUpperBound(r, v)`, with the getters of the same
names; the column setters also accept a container or a map of columns, as
`addColSet()` does, to give the same bounds to all of them. Names are given by
`colName(c, s)` and `rowName(r, s)`, read by `colName(c)` and `rowName(r)`,
and searched by `colByName(s)` and `rowByName(s)`, which return `INVALID` when
no item has the name.

The objective is set by `obj(e)`, whose constant term is kept by `LpBase`
itself and added to the objective value of the solution, and read by `obj()`;
`objCoeff(c, v)` and `objCoeff(c)` set and read one coefficient. The direction
is set by `sense(MIN)` or `sense(MAX)`, or by the shorthands `min()` and
`max()`, and read by `sense()`. Finally, `clear()` empties the model,
`messageLevel(level)` sets how much the solver prints (all the backends start
at `MESSAGE_NOTHING`), and `solverName()` returns the name of the backend.
Also, `write(file, format)` writes the model to a file, by default in the
format `"MPS"`; a format that the backend does not support throws
`LpBase::UnsupportedFormatError` (Table 20.2).

## 20.4 Solving an LP and reading the solution {#sec-20-4}

For an LP, i.e., (20.1) with $J=\emptyset$, the class `LpSolver` adds the
solution. We recall the optimality conditions that its dual values satisfy,
for a minimization with finite bounds. With $y$ the dual values of the rows
and $d=c-A^\top y$ the reduced costs of the columns, a feasible $x$ is optimal
if and only if there is a $y$ such that

$$
y_i > 0 \Rightarrow (Ax)_i = l^r_i ,\quad y_i < 0 \Rightarrow (Ax)_i = u^r_i ,\quad d_j > 0 \Rightarrow x_j = l^c_j ,\quad d_j < 0 \Rightarrow x_j = u^c_j . \tag{20.2}
$$

Thus, the dual value of a row is the derivative of the optimal value with
respect to the bound that is active, and its sign indicates which bound it is
(the interface passes on the dual values of the solver unchanged, and hence
their sign convention, in particular for a maximization, is the one of the
solver). The theory is in any textbook on linear programming, e.g., [Dantzig
1963](Z-bibliography.md#ref-dantzig63linearprog).

A call of `solve()` solves the problem and returns the `SolveExitStatus` of
[§20.1](20-lp.md#sec-20-1). The *problem type* of the primal and of the dual
problem is then read by `primalType()` and `dualType()`, of the enumeration
`LpSolver::ProblemType`: `UNDEFINED` (no feasible solution found, although one
may exist), `INFEASIBLE`, `FEASIBLE` (a feasible solution found, its
optimality not proved), `OPTIMAL` and `UNBOUNDED`. The values of a solution
are read by `primal(c)` for a column, `primal(e)` for an expression (the
scalar product with the primal solution plus the constant term), `dual(r)` for
a row and `dual(e)` for a `DualExpr`. As for the objective value, `primal()`
includes the constant term of the objective; according to the documentation,
it is `INF` or `-INF` for an infeasible or unbounded problem, depending on the
direction, and NaN when no primal solution is found. Also, the basis is read
by `colStatus(c)` and `rowStatus(r)`, of the enumeration `VarStatus`: `BASIC`,
`FREE` (nonbasic and free), `LOWER` and `UPPER` (nonbasic at a bound) and
`FIXED` (nonbasic and fixed).

When the problem has no optimal solution, the rays certify it, in the backends
that provide them. The *primal ray* `primalRay(c)` is a solution of the primal
problem with each finite bound replaced by 0 and a negative (for a
minimization) objective value; it proves that the dual problem is infeasible,
and, when the primal problem is feasible, that the latter is unbounded. The
*dual ray* `dualRay(r)` is, symmetrically, a solution of the dual problem with
each finite objective coefficient of it, i.e., each finite primal bound,
replaced by 0, with a positive objective value; it proves the primal problem
infeasible. The header warns that some solvers may not compute the rays.
Finally, `newSolver()` returns a new empty solver of the same type, and
`cloneSolver()` a copy of the problem; both return a pointer that the caller
deletes.

## 20.5 Mixed integer programs {#sec-20-5}

In `MipSolver` one describes (20.1) with integer columns. The type of a column
is set by `colType(c, type)` and read by `colType(c)`, of the enumeration
`MipSolver::ColTypes`: `REAL` (the default) or `INTEGER`; a binary column is
an integer one with the bounds 0 and 1. As for an LP, `solve()` returns
`SOLVED` or `UNSOLVED`, and `type()` returns the problem type, with the same
five values as `LpSolver::ProblemType`; `UNBOUNDED` means that the MIP, or at
least its continuous relaxation, is unbounded. The solution is read by
`sol(c)`, `sol(e)` and `solValue()`, the last one including the constant term
of the objective. A MIP solver gives no dual values and no basis.

The integrality of a column whose bounds are not integer deserves a remark
(cf. Exercise 20.5). The integer values of such a column are those of
$[\lceil l^c_j\rceil, \lfloor u^c_j\rfloor]$, and the problem is infeasible
when this interval is empty. GLPK refuses such a column, and Cbc does not
round its bounds; hence, `GlpkMip` and `CbcMip` round the bounds of each
integer column inwards before the solve, up to an integer tolerance of
$10^{-6}$, as in Algorithm 20.1, which is the one of `GlpkMip::_solve()`.

<span id="alg-20-1"></span>**Algorithm 20.1** (The solve of `GlpkMip`).

```
1  solve the continuous relaxation by the dual simplex method
   (on a bad basis, build an advanced basis and solve once more)
2  if the relaxation is not optimal: return SOLVED (type: of the relaxation)
3  for each integer column j with a finite bound:
4      l' := ceil(l_j - 1e-6); u' := floor(u_j + 1e-6)
5      if l' > u': the problem is INFEASIBLE; skip the search
6      else give the column the bounds [l', u'] (fixed if l' = u')
7  run the branch and cut of GLPK (glp_intopt)
8  give back the bounds given by the user; return SOLVED or UNSOLVED
```

`CbcMip` rounds the bounds in the same way in the copy of the problem that it
gives to Cbc, and it also leaves the bounds of the model unchanged. The test
`test/mip_test.cc` checks both that the bounds stay as they were given and
that a column without integer values makes the problem infeasible.

!!! note "abLEMON"
    The rounding of the bounds of the integer columns in `GlpkMip` and
    `CbcMip` is new in abLEMON (version 1.4.1): GLPK 5.0 refused such a
    column, which left the problem unsolved, and Cbc gave a solution beyond
    the bound. Also, `CbcMip` no longer reports a proven infeasible problem as
    feasible (trac #626, version 1.4.0).

## 20.6 The backends {#sec-20-6}

Each backend wraps one solver and adds a few functions of its own. Table 20.2
summarizes them, and the paragraphs below give the details.

| Class | Solver | `solve()` | Other solves | Formats of `write()` |
|----------|----------------------------|-----------------------|----------------------------|------------------------|
| `GlpkLp` | [GLPK](Z-bibliography.md#ref-glpk) | primal simplex | `solvePrimal()`, `solveDual()` | `"MPS"`, `"LP"` |
| `GlpkMip` | [GLPK](Z-bibliography.md#ref-glpk) | Algorithm 20.1 | | `"MPS"`, `"LP"` |
| `CplexLp` | [CPLEX](Z-bibliography.md#ref-cplex) | `CPXlpopt` | `solvePrimal()`, `solveDual()`, `solveBarrier()` | `"MPS"`, `"LP"`, `"SOL"` |
| `CplexMip` | [CPLEX](Z-bibliography.md#ref-cplex) | branch and cut of CPLEX | | `"MPS"`, `"LP"`, `"SOL"` |
| `ClpLp` | [Clp](Z-bibliography.md#ref-clp) | primal simplex | `solvePrimal()`, `solveDual()`, `solveBarrier()` | `"LP"` |
| `CbcMip` | [Cbc](Z-bibliography.md#ref-cbc) | branch and cut of Cbc | | none |
| `SoplexLp` | [SoPlex](Z-bibliography.md#ref-soplex) | simplex of SoPlex | | none |

<span id="tab-20-2"></span>**Table 20.2.** The backends, the method of
`solve()`, the other solve functions, and the formats accepted by `write()`;
any other format throws `UnsupportedFormatError`.

**GLPK.** `GlpkLp` and `GlpkMip` share the base `GlpkBase`, whose `lpx()`
returns the pointer to the problem object of GLPK (as a `void *` that converts
to the pointer type of GLPK), and whose `lpxRow(r)` and `lpxCol(c)` give the
indices that GLPK uses. Each solve function of `GlpkLp` runs the simplex
method of GLPK; when it reports a bad, singular or ill-conditioned basis, it
builds an advanced basis by `glp_adv_basis()` and runs once more, and it
returns `UNSOLVED` if this fails too. The function `presolver(bool)` turns the
presolver of GLPK on or off, and it is off by default. Also, a static member
of `GlpkBase` of the private type `FreeEnvHelper` frees the environment of
GLPK (`glp_free_env()`) when the program ends.

**CPLEX.** `CplexLp` and `CplexMip` share the base `CplexBase`, whose
`cplexEnv()` and `cplexLp()` return the environment and the problem objects of
CPLEX, and whose `env()` returns the `CplexEnv` in use. A `CplexEnv` wraps the
environment of CPLEX with a reference count protected by a lock, so that
several problems can share one environment (and one license): the constructors
of `CplexLp` and `CplexMip` that take a `CplexEnv` use the given one, and the
others open a new one. When the license check fails, the constructor of
`CplexEnv` throws `CplexEnv::LicenseError`, whose `what()` gives the message
of CPLEX. In `CplexLp`, `solve()` calls `CPXlpopt`, which lets CPLEX choose
the method, and the three other functions force the primal simplex, the dual
simplex and the barrier method.

**Clp and Cbc.** `ClpLp` wraps a `ClpSimplex` object of
[Clp](Z-bibliography.md#ref-clp); `solve()` runs the primal simplex method,
and `clpRow(r)` and `clpCol(c)` give the indices of Clp. Note that `ClpLp`
writes only the format `"LP"`, and therefore `write(file)` with the default
`"MPS"` throws. `CbcMip` keeps the model in a `CoinModel` of
[Cbc](Z-bibliography.md#ref-cbc), and at each solve it copies the model into a
new `OsiClpSolverInterface` (with the rounding of [§20.5](20-lp.md#sec-20-5))
and solves the continuous relaxation. When this is optimal, it runs the branch
and cut of Cbc with a fixed set of cut generators (probing, Gomory, knapsack
cover, odd hole, clique, mixed integer rounding and flow cover) and of primal
heuristics (rounding, local search, greedy cover, feasibility pump and RINS).

**SoPlex.** `SoplexLp` wraps the class `SoPlex` of
[SoPlex](Z-bibliography.md#ref-soplex). Its message level `MESSAGE_NOTHING`
maps to the verbosity of errors of SoPlex, which is (apparently) the lowest
one SoPlex offers. Its primal ray is the one of SoPlex, and its dual ray is
the Farkas proof of the infeasibility of the primal problem.

!!! note "abLEMON"
    `SoplexLp` works with SoPlex 5 and later, through the API of its class
    `SoPlex`; in LEMON 1.3.1 it did not compile with these versions, and it
    gave the Farkas proof of the dual as its primal ray (version 1.5.0).
    SoPlex is found through its CMake configuration.

## 20.7 The skeletons {#sec-20-7}

The header `lp_skeleton.h` declares `LpSkeleton` and `MipSkeleton`, which
derive from `LpSolver` and `MipSolver` and from the common base
`SkeletonSolverBase`. They implement the virtual functions of the interface by
doing (almost) no work: the coefficients, the bounds and the names are not
stored, the getters return 0 (or `MIN` for the sense, and `-1`, i.e.,
`INVALID`, for a search by name), `solve()` returns `SOLVED`, the problem
types are `UNDEFINED`, the basis statuses are `BASIC`, `write()` writes
nothing, and `newSolver()` and `cloneSolver()` return a null pointer. Their
names are `"LpSkeleton"` and `"MipSkeleton"`. On a skeleton, however, all that
`LpBase` keeps works as with a real solver: the index of the columns and of
the rows, and hence `ColIt`, `RowIt`, `cols()`, `rows()` and the handles, and
the classes `Expr`, `DualExpr` and `Constr` with their operators, which do not
involve the solver at all.

We see two uses of the skeletons. First, a program can build and check a
model, e.g., count its columns and rows, without any solver; `test/lp_test.cc`
does so in all configurations, and so does the example of
[§20.8](20-lp.md#sec-20-8). Second, they are the starting point for a new
backend, which must implement the pure virtual functions declared in
`lp_base.h`: `_addCol()`, `_addRow()`, `_eraseCol()`, `_eraseRow()`, the
functions of the names, of the coefficients (`_setRowCoeffs()`,
`_getRowCoeffs()`, `_setColCoeffs()`, `_getColCoeffs()`, `_setCoeff()`,
`_getCoeff()`), of the bounds, of the objective and of the sense, `_clear()`,
`_solverName()` and `_messageLevel()`. An LP backend also implements
`_solve()`, the getters of the solution, of the rays, of the basis and of the
problem types, `newSolver()` and `cloneSolver()`; a MIP backend implements
`_solve()`, `_setColType()`, `_getColType()`, `_getType()`, `_getSol()` and
`_getSolValue()`. The coefficients reach the backend through two protected
iterators of `LpBase`: `ExprIterator` lists the terms of an expression as
pairs of a solver index and a value, and `InsertIterator` stores the pairs
returned by the solver into an expression, translating the indices. The
function `_addRow(l, b, e, u)`, which adds a row with its coefficients and
bounds in one call, and `_write()` have default implementations, the latter
throwing `UnsupportedFormatError`.

## 20.8 An example {#sec-20-8}

Our program writes the maximum flow problem on a digraph $G=(N,A)$ with
capacities $u$, a source $s$ and a sink $t$ as the LP

$$
\max \sum_{a\in\delta^+(s)} x_a - \sum_{a\in\delta^-(s)} x_a \quad\text{s.t.}\quad \sum_{a\in\delta^-(v)} x_a = \sum_{a\in\delta^+(v)} x_a \ \ (v\in N\setminus\{s,t\}) ,\quad 0\le x_a\le u_a \ \ (a\in A) , \tag{20.3}
$$

in a function that takes any `LpSolver`, with one column per arc obtained by
`addColSet()` on an arc map. First, the model is built on an `LpSkeleton`, on
which the program checks the number of columns and rows and the algebra of the
expressions and constraints of Table 20.1. When the library has an LP backend,
the same function builds the model on the default solver `Lp`, which solves
it, and the program compares the optimal value with the one of `Preflow`
([chapter 12](12-max-flow.md#ch-12)); without a backend this part is left out
by `#ifdef LEMON_HAVE_LP`, and the program still compiles and checks the rest.

<span id="ex-20-1"></span>**Exercise 20.1.** Write the shortest path problem
from $s$ to $t$ as an LP with one column per arc, solve it with the default
solver, and compare its value with the distance computed by `Dijkstra`
([chapter 10](10-shortest-paths.md#ch-10)); read the dual values of the rows
