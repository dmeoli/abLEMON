# 21. Input and output {#ch-21}

This chapter describes how graphs and the data attached to them are read from
and written to files. The format of the library is the LEMON Graph Format
(LGF), read by the classes of `lgf_reader.h` and written by those of
`lgf_writer.h` ([§21.1](21-io.md#sec-21-1) to [§21.4](21-io.md#sec-21-4)).
Besides it, `dimacs.h` reads the formats of the first DIMACS implementation
challenge and writes one of them ([§21.5](21-io.md#sec-21-5)),
`nauty_reader.h` reads the graph6 format of the nauty package
([§21.6](21-io.md#sec-21-6)), and `graph_to_eps.h` draws a graph in
Encapsulated PostScript ([§21.7](21-io.md#sec-21-7)). A malformed input makes
the readers and the writers throw `FormatError`, and a file that cannot be
opened makes them throw `IoError` ([chapter 8](08-auxiliary.md#ch-8)); both
derive from `Exception`.

## 21.1 The LEMON Graph Format {#sec-21-1}

An LGF file is a text file made of *sections*, each opened by a header line
whose first character is `@`, followed by the type of the section and by an
optional name, the *caption*, which distinguishes sections of the same type. A
line whose first non-blank character is `#` is a comment, and the empty lines
are ignored; whatever precedes the first header is skipped. The standard types
are `@nodes`, `@arcs` (with its synonym `@edges`) and `@attributes` for
digraphs and graphs, and `@red_nodes` and `@blue_nodes` for the two node sets
of a bipartite graph. A file may contain other sections, whose content is free
([§21.4](21-io.md#sec-21-4)).

Standard sections are made of *tokens* separated by white space. A token is
either plain, i.e., a sequence of characters other than white space, or
quoted, i.e., enclosed in double quotes, in which case it may contain white
space. In both kinds a backslash introduces an escape sequence of C: `\\`,
`\"`, `\'`, `\?`, `\a`, `\b`, `\f`, `\n`, `\r`, `\t`, `\v`, a character in
octal (one to three digits) or in hexadecimal (`\x` with one or two digits).
Moreover, the node and arc sections are *column oriented*: their first line
gives the names of the maps, and each following line, up to the next header,
gives the values of these maps for one item. A short file shows the structure:

```
@nodes
label  name
0      "the source"
1      a
2      t
@arcs
          label  capacity
0    1    0      16
0    2    1      12
1    2    2      4
@attributes
source  0
target  2
```

In a node section, the map named `label` plays a special role, since its
values identify the nodes in the rest of the file; it is needed whenever the
arcs or the attributes refer to the nodes. In an arc section, each line starts
with the labels of the source and of the target node, followed by the values
of the maps; the map `label` is optional here, and it identifies the arcs for
the attributes. A section without maps must contain a single `-` in its first
line. For an undirected graph, the section `@edges` (or `@arcs`) describes the
edges, and two columns whose names are the name of a map prefixed with `+` and
`-` hold the values of an arc map on the two arcs of each edge. Each line of
the section `@attributes` consists of two tokens, a name and a value; the
value may be the label of a node or of an edge, and the label of an edge
prefixed with `+` or `-` refers to the forward or the backward arc of that
edge. For a bipartite graph, the sections `@red_nodes` and `@blue_nodes`
replace `@nodes`, each with its own maps; a map present in both sections can
be read as a node map.

## 21.2 Reading {#sec-21-2}

We now describe `DigraphReader< DGR >`, which reads an LGF file into a digraph
of type `DGR` by *batch processing*. One creates a reader, adds to it the
rules that specify which maps and attributes are wanted and where they go, and
executes them by `run()`, which reads the file once. The functions that add
the rules return a reference to the reader, and are therefore chained:

```
DigraphReader< ListDigraph >( g , std::cin )
  .arcMap( "capacity" , cap ).node( "source" , s ).run();
```

Its three constructors take the digraph and an input stream (by default
`std::cin`), a file name as a `std::string` or a file name as a
`const char *`; the last two open the file and throw `IoError` when they
cannot. With the same three kinds of source, `digraphReader()` returns a
reader, which lets one write the chain without naming the type (the reader
returned is moved, not copied).

!!! note "abLEMON"
    The readers and the writers take over the stream of the object returned by
    `digraphReader()` and the like through a constructor that takes it by
    rvalue reference, which C++23 requires; in LEMON 1.3.1 it took a
    non-constant lvalue reference, and the LGF classes did not compile under
    C++23 (version 1.4.0).

We now list the reading rules. A rule `nodeMap(caption, map)` reads the column
`caption` of the node section into `map`, a writable node map, and
`arcMap(caption, map)` does the same for the arc section; one column can be
read into several maps. The value of each token is converted to the value type
of the map by `operator>>` of a `std::istringstream`, and the token must be
read whole: a token that cannot be converted, or that leaves characters
behind, throws `FormatError`. A token read into a `std::string` is taken as it
is. The overloads `nodeMap(caption, map, converter)` and
`arcMap(caption, map, converter)` take instead a functor from `std::string` to
the value type. The rules `attribute(caption, value)` and
`attribute(caption, value, converter)` read an attribute into a variable, and
`node(caption, n)` and `arc(caption, a)` read an attribute whose value is a
label into a node or an arc handle.

By default the reader uses the first section of each type. The functions
`nodes(caption)`, `arcs(caption)` and `attributes(caption)` select instead the
section of that type with the given caption. With `useNodes(map)` the nodes
are taken as already existing, and they are not created: `map` gives the label
of each existing node (its values are turned into strings by `operator<<`, or
by a converter in the overload `useNodes(map, converter)`), and the node
section only identifies the nodes by their labels, reading the other maps into
them. Similarly, `useArcs(map)` and `useArcs(map, converter)` reuse the
existing arcs. These functions allow a *multipass* reading, e.g., to read a
node set and one arc section into a digraph in a first pass, and a second arc
section into an arc set of [chapter 4](04-graphs.md#ch-4) in a second pass.
The functions `skipNodes()` and `skipArcs()` leave a section out: the nodes
are then not created, and the arcs can only be read if `useNodes()` gives the
labels.

<span id="alg-21-1"></span>**Algorithm 21.1** (The reading of an LGF file by
`run()`).

```
1  skip the lines before the first header
2  for each header "@type caption":
3      if type is nodes and none was read, and the caption matches:
4          read the map names; each line: tokens -> new node (or the node
           of its label, with useNodes); store the label; apply the rules
5      elif type is arcs or edges, likewise, the first two tokens being
           the labels of the source and of the target
6      elif type is attributes, likewise: each line is a name and a value,
           given to all the rules of that name
7      else skip the section
8  throw FormatError if the node or the arc section was not found (unless
   skipped), or if attribute rules exist and no attribute section was read
```

Note that the checks are rather strict. A map named by a rule and absent from
the header, a column missing in a line, an extra token at the end of a line, a
label not found, a map name repeated in a header and an attribute repeated in
its section all throw `FormatError`; so does an attribute required by a rule
and absent from the section. In all cases, the error carries the line number
and, when the reader was opened on a file, the file name, and its `what()`
gives both. Since the labels are kept in a `std::map` from the token to the
item, reading $n$ nodes and $m$ arcs costs $O((n+m)\log n)$ string
comparisons, besides the conversions.

For an undirected graph one uses `GraphReader< GR >`, which reads it in the
same way, with the rules `nodeMap()`, `edgeMap()`, `attribute()`, `node()` and
`edge()`, the selection functions `nodes()`, `edges()` and `attributes()`, and
`useNodes()`, `useEdges()`, `skipNodes()` and `skipEdges()`. Its rule
`arcMap(caption, map)` reads the two columns `+caption` and `-caption` into
the values of an arc map on the forward and the backward arc of each edge, and
`arc(caption, a)` reads an attribute whose value is an edge label with a sign.
Similarly, `BpGraphReader< BGR >` reads a bipartite graph from the sections
`@red_nodes`, `@blue_nodes` and `@edges`, all three of which must be present;
it adds the rules `redNodeMap()`, `blueNodeMap()`, `redNode()` and
`blueNode()`, and its `nodeMap()` reads a map that both node sections contain.
The functions `graphReader()` and `bpGraphReader()` return readers as
`digraphReader()` does. In the code, each rule is an object of the namespace
`_reader_bits`: a `MapStorage` (or a `GraphArcMapStorage`, for the two columns
of an arc map) for a map, and a `ValueStorage` for an attribute. The label of
an attribute is resolved by a `MapLookUpConverter`, a
`DoubleMapLookUpConverter` (for a node of a bipartite graph, searched among
the red and the blue labels) or a `GraphArcLookUpConverter` (for a signed edge
label).

## 21.3 Writing {#sec-21-3}

Symmetrically, `DigraphWriter< DGR >` writes a digraph in the same batch
style: the rules `nodeMap(caption, map)`, `arcMap(caption, map)`,
`attribute(caption, value)`, `node(caption, n)` and `arc(caption, a)`,
executed by `run()`. Its constructors take the digraph and an output stream
(by default `std::cout`) or a file name, and throw `IoError` when the file
cannot be opened; `digraphWriter()` returns a writer in the same three ways.
Each value of a map or of an attribute is converted to a token by `operator<<`
of a `std::ostringstream`, or by a functor from the value type to
`std::string` given as the third argument of the rule. A token that is empty,
starts with `@`, or contains white space or one of the characters `\`, `"`,
`'`, `\a` and `\b`, is written quoted and with escapes; the others are written
as they are. We remark that the default conversion writes a `double` with the
default precision of the streams, i.e., 6 significant digits, so that a file
written with it does not give back the same values when it is read; a
converter that writes 17 significant digits (as in the example of
[§21.8](21-io.md#sec-21-8)) avoids this.

Each item gets a label from the writer. If a map is written under the name
`label`, its values are the labels, and the items are written in the order of
these values (an order that `operator<` must define, otherwise `FormatError`
is thrown). Otherwise the writer adds a column `label` with the ids of the
items, and writes them in the order of the ids. Hence, the arc section always
has the label column, and therefore it never needs the `-` of
[§21.1](21-io.md#sec-21-1). The functions `nodes(caption)`, `arcs(caption)`
and `attributes(caption)` give a caption to the sections, `skipNodes()` and
`skipArcs()` leave a section out (its labels are still computed, for the
sections that follow), and `ostream()` returns the stream of the writer. These
allow writing two arc sections in two passes on the same stream: the second
writer skips the nodes and appends its arc section to the output of the first.

Note that the writer keeps the maps and the values of the rules by reference,
and reads them only in `run()`. Thus, they must exist until then. A temporary
passed to a rule lives until the end of the full expression that contains it;
this is enough in a chain that ends with `run()`, but not when the rules and
`run()` are separated.

!!! note "abLEMON"
    The documentation of the writers states that the values of their rules are
    kept by reference; in LEMON 1.3.1 the test of the format passed a
    temporary arc to a writer, which read it after its end (trac #683, version
    1.4.0).

For an undirected graph, `GraphWriter< GR >` is used, with `edgeMap()` and
`edge()` for the edges and an `arcMap()` that writes the columns `+caption`
and `-caption`; the rule `arc(caption, a)` writes the label of the edge of `a`
with the sign of its direction. Similarly, `BpGraphWriter< BGR >` writes the
sections `@red_nodes`, `@blue_nodes` and `@edges`, with the rules
`redNodeMap()`, `blueNodeMap()`, `redNode()` and `blueNode()`; its `nodeMap()`
writes the map in both node sections, and its `nodes(caption)` gives the
caption to both. The functions `graphWriter()` and `bpGraphWriter()` return
writers. Their rules are objects of the namespace `_writer_bits` with the same
names as those of the readers (`MapStorage`, `GraphArcMapStorage`,
`ValueStorage`, `MapLookUpConverter`, `DoubleMapLookUpConverter` and
`GraphArcLookUpConverter`), and the items are sorted by their labels through
the comparators `MapLess` and `GraphArcMapLess`.

## 21.4 Extra sections and the contents of a file {#sec-21-4}

Sections of other types are read by `SectionReader` and written by
`SectionWriter`, which are constructed, like the other readers and writers,
from a stream or a file name, or returned by `sectionReader()` and
`sectionWriter()`. In a `SectionReader`, `sectionLines(type, functor)` gives
each line of the section `@type` to a functor that takes a `std::string`,
after the empty lines and the comments have been removed and the leading white
space trimmed; `sectionStream(type, functor)` instead calls once a functor
that takes the `std::istream &` and an `int &` line number, which it reads
from and updates. A section is read at most once (a second section of the same
type throws `FormatError`), and `run()` throws `FormatError` when a section
with a rule is missing. In a `SectionWriter`, `sectionLines(type, generator)`
writes the strings returned by a functor without arguments until it returns an
empty string, and `sectionStream(type, functor)` lets a functor write to the
stream, its last line ending with a newline. The two kinds of rules are stored
as objects of the classes `LineSection` and `StreamSection` of the namespaces
`_reader_bits` and `_writer_bits`. These classes act on the extra sections
only, and they can be run on the same file as the graph readers, which skip
the sections they do not know.

Finally, `LgfContents` reads a file without knowing its contents and records
its structure, for general tools that must guess what a file holds. After
`run()`, `nodeSectionNum()`, `nodeSection(i)` and `nodeMapNames(i)` give the
number of node sections, the caption of the $i$-th one and the names of its
maps; `arcSectionNum()`, `arcSection(i)` and `arcMapNames(i)` do the same for
the arc and edge sections, with the synonyms `edgeSectionNum()`,
`edgeSection(i)` and `edgeMapNames(i)`. Also, `attributeSectionNum()`,
`attributeSectionNames(i)` and `attributes(i)` describe the attribute
sections, and `extraSectionNum()` and `extraSection(i)` give the types of the
other sections.

## 21.5 The DIMACS formats {#sec-21-5}

We now turn to the formats of the first DIMACS implementation challenge
([Johnson and McGeoch 1993](Z-bibliography.md#ref-johnson1993network)). They
are line oriented: a line starting with `c` is a comment, the line
`p type n m` gives the type of the problem and the numbers of nodes and arcs,
a line starting with `n` describes a node, and a line starting with `a` an
arc, the nodes being numbered from 1. A call of `dimacsType(is)` reads the
comments and the problem line, and returns a `DimacsDescriptor`, whose fields
are the `type` (`NONE`, `MIN`, `MAX`, `SP` or `MAT`), the `nodeNum` and the
`edgeNum`; an unknown type, a missing problem line or another line before it
throws `FormatError`. Each reader takes the descriptor as its last, optional,
argument; without it, the reader calls `dimacsType()` itself, and with it, the
reader continues on the stream where `dimacsType()` stopped. A reader clears
the graph, creates the $n$ nodes in order, and throws `FormatError` when the
type of the file is not the one it reads.

| Function | Type | Lines read | Data written |
|----------------------------|-------------|----------------------------|----------------------------|
| `readDimacsMin(is, g, lower, capacity, cost, supply, infty, desc)` | `min` | `n id supply`, `a u v low cap cost` | lower bounds, capacities, costs, supplies (0 when absent) |
| `readDimacsMax(is, g, capacity, s, t, infty, desc)` | `max` | `n id s`, `n id t`, `a u v cap` | capacities, source, target |
| `readDimacsSp(is, g, length, s, desc)` | `sp` | `n id`, `a u v len` | lengths, source |
| `readDimacsCap(is, g, capacity, infty, desc)` | `max` or `sp` | `a u v cap` | capacities (or lengths) |
| `readDimacsMat(is, g, desc)` | `mat` | `a u v` | the arcs (or edges) |

<span id="tab-21-1"></span>**Table 21.1.** The DIMACS readers of `dimacs.h`;
the problem line and the comments are read as described in the text.

An infinite capacity is written in the DIMACS files in two ways, and the
readers translate both into the value `infty`. In a `min` file, an arc whose
capacity is smaller than its lower bound gets the capacity `infty`, and in a
`max` file (also through `readDimacsCap()`) an arc with a negative capacity
gets it. When `infty` is 0, its default, the readers take
`std::numeric_limits< Capacity >::infinity()` if the type has an infinity, and
its maximum value otherwise. As for `readDimacsMat()`, it adds an edge for
each `a` line to an undirected graph, and an arc to a digraph; note that it
reads only the `a` lines, and the `e` lines that some matching and clique
files use are skipped. Conversely, `writeDimacsMat(os, g, comment)` writes a
digraph in the format `mat`, i.e., an optional comment line, the problem line,
and one `a` line per arc; the nodes are numbered from 1 in the order of the
node iterator.

!!! note "abLEMON"
    `dimacsType()` is inline, and hence two translation units that include
    `dimacs.h` link together, which they did not in LEMON 1.3.1 (version
    1.4.0).

## 21.6 The graph6 format of nauty {#sec-21-6}

Our next format comes from the program `geng` of the nauty package ([McKay and
Piperno 2014](Z-bibliography.md#ref-mckay2014practical)) generates all the
non-isomorphic undirected graphs of a class with a given number of nodes,
writing one graph per line in the *graph6* format. A call of
`readNautyGraph(graph, is)` reads one line of the stream (by default
`std::cin`) and builds the graph it describes, after clearing `graph`; it
returns the stream, and it can thus be used as the condition of a loop that
reads a whole file. In graph6, each character carries six bits, its code minus
63, and the upper triangle of the adjacency matrix is listed column by column.

<span id="alg-21-2"></span>**Algorithm 21.2** (The decoding of a graph6 line).

```
1  skip the header ">>graph6<<" if the line starts with '>'
2  c := next character - 63
3  if c < 63: n := c
4  else: n := the 18 bits of the next three characters (minus 63 each)
5  create n nodes
6  for j := 1 to n - 1, for i := 0 to j - 1:
7      take the next bit, from the most significant of each character;
       if it is 1, add the edge {i, j}
```

For instance, the line `D~{` describes the complete graph on 5 nodes: `D`
gives $n=68-63=5$, and `~{` give the bits 111111 and 1111 of the 10 pairs,
followed by two bits of padding. Note that the function does not check the
length of the line, and therefore a truncated line is read past its end. The
header suggests to pipe the output of `geng` into the program, since the files
are large.

## 21.7 Drawing a graph in EPS {#sec-21-7}

A call of `graphToEps(g, os)` draws a graph or a digraph as an Encapsulated
PostScript picture on a stream (by default `std::cout`); the overloads
`graphToEps(g, file_name)` write to a file, which they open and close
themselves, and throw `IoError` when they cannot open it. It returns an object
of the class `GraphToEps`, whose member functions set the parameters of the
picture by the technique of the named parameters ([chapter
3](03-mental-model.md#ch-3)), and whose `run()` writes it. Nothing is written
without `run()`, which therefore must close the chain.

```
graphToEps( g , "flow.eps" ).coords( coords ).arcWidths( cap )
  .autoArcWidthScale().drawArrows().title( "a flow problem" ).run();
```

The maps of the picture are given by functions that return a new object with
the type of the map, and they are kept by reference. First, `coords(map)`
gives the position of each node, a node map with values of type `dim2::Point`
([chapter 8](08-auxiliary.md#ch-8)), without which all the nodes are drawn at
the point $(1,1)$. Then `nodeSizes(map)`, `nodeShapes(map)`,
`nodeColors(map)`, `nodeTexts(map)`, `nodeTextColors(map)` and
`nodePsTexts(map)` set the size, the shape (`CIRCLE`, `SQUARE`, `DIAMOND`,
`MALE`, `FEMALE`, i.e., 0 to 4), the color, a text written on the node (of any
type that `operator<<` writes), its color, and a block of PostScript code
drawn at the node; and `arcWidths(map)` and `arcColors(map)` set the width and
the color of the arcs. Colors are objects of the class `Color` of `color.h`,
and a `Palette` composed with an integer map (`composeMap()`, [chapter
6](06-maps.md#ch-6)) gives distinct colors.

Other parameters are set by functions that return the same object. Usually one
scales the sizes by `nodeScale(d)` (0.01 by default) and `arcWidthScale(d)`
(0.003), and both are relative to the diagonal of the bounding box of the
nodes, unless `absoluteNodeSizes()` and `absoluteArcWidths()` make them
absolute; `autoNodeScale()` and `autoArcWidthScale()` rescale them so that the
largest size equals the scale. Similarly, `scale(d)` scales the picture; by
default, `preScale()` multiplies or divides the scale by powers of 10 until
the bounding box is between 100 and 1000 points, and `preScale(false)` turns
this off. Also, `scaleToA4()` fits the picture to an A4 page, `border(b)` and
`border(x, y)` set the margin (10 points by default), and `negateY()` flips
the vertical axis. As for the arcs, `drawArrows()` draws the arrowheads, whose
size `arrowLength(d)` and `arrowWidth(d)` set, and `enableParallel()` draws
parallel arcs as distinct curves at the distance `parArcDist(d)`. Finally,
`hideNodes()` and `hideArcs()` leave the nodes or the arcs out,
`nodeTextSize(d)` sets the size of the texts, and `distantColorNodeTexts()`
and `distantBWNodeTexts()` color each text so that it stands out on its node.
The functions `undirected()` and `directed()` choose whether the edges of an
undirected graph are drawn once (the default for undirected graphs) or as two
arcs, and `title(t)` and `copyright(t)` write the DSC fields `%%Title` and
`%%Copyright` of the header, which also gets the creation date. Also,
`edgeWidths()`, `edgeColors()`, `edgeWidthScale()`, `autoEdgeWidthScale()`,
`absoluteEdgeWidths()`, `parEdgeDist()` and `hideEdges()` are aliases of the
functions on the arcs. The demo `graph_to_eps_demo` ([chapter
22](22-tools.md#ch-22)) uses most of these parameters.
